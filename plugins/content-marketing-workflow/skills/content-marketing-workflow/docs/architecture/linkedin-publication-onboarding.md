# LinkedIn publication onboarding

Date: 2026-09-04
Status: normative generic onboarding contract

## Purpose

Defines the guided setup and resume flow for the LinkedIn member-profile publication adapter.

This document contains generic behavior only. Concrete member identity, application identifiers, site URL, repository connection, preferred publication time and token expiration metadata belong to the active user/project profile.

## Supported target

Current adapter target:

```text
authenticated LinkedIn member profile
```

The current Bridge does not treat organization/Page publication as equivalent to this member-profile adapter.

## Required LinkedIn products/scopes

Current baseline:

```text
Share on LinkedIn -> w_member_social
Sign in with LinkedIn using OpenID Connect -> openid + profile
```

Requested scope string:

```text
openid profile w_member_social
```

Do not request broader LinkedIn permissions unless a separately implemented capability requires them.

## Secret boundary

Never ask the user to paste into chat or GitHub:

```text
Client Secret
access token
refresh token
OAuth authorization code
```

The Client Secret and resulting access token remain on the WordPress side in SEO Workflow Bridge.

The active user profile may retain only non-secret lifecycle metadata, including:

```yaml
platform: linkedin
remote_id: <member URN/subject>
remote_name: <member display name>
required_scopes: [openid, profile, w_member_social]
credential:
  secret_location: wordpress_seo_workflow_bridge
  token_expires_at: <timestamp|null>
  last_observed_valid: true|false|null
  last_observed_at: <timestamp|null>
```

## Setup flow

### 1. Resolve or create the LinkedIn application

Guide the user through LinkedIn Developers only when no suitable application is already configured.

Record non-secret application metadata in user/project data when needed for resume. Do not store the Client Secret there.

### 2. Enable required products

Require the products/scopes listed above. If LinkedIn's UI changes, guide from the actual screen and update the generic onboarding contract only when the product behavior itself changed.

### 3. Configure the exact callback URL

Use the callback generated by the user's active WordPress Bridge:

```text
<wordpress-site>/wp-json/seo-workflow-bridge/v1/linkedin/oauth/callback
```

The actual URL belongs to the user's WordPress connection metadata, not to the skill.

### 4. Configure WordPress Bridge

Open:

```text
WordPress administration
-> Settings
-> SEO Workflow Bridge - LinkedIn
```

Enable LinkedIn support and enter the application's Client ID plus Client Secret directly in WordPress.

The secret field must not render the stored secret back in clear text.

### 5. Connect LinkedIn

Run the Bridge connection action. The Bridge:

```text
creates bounded OAuth state
-> redirects to LinkedIn
-> exchanges the returned authorization code server-side
-> verifies member identity through LinkedIn userinfo
-> stores the access token only in WordPress
-> persists non-secret member identity separately in WordPress
```

Connection itself does not authorize any post.

### 6. Read-only verification

Require Bridge state showing:

```text
enabled
connected
member_verified
expected scopes
known token expiry when supplied by LinkedIn
```

The skill reconciles non-secret member identity and token expiry into the active user profile.

## Scheduled publication

Authorized scheduled publication uses:

```text
POST /wp-json/seo-workflow-bridge/v1/linkedin/publish-authorized
```

Current scheduling path:

```text
exact approved post
-> timezone-aware planned_at
-> exact LinkedIn authorization record
-> temporary verified delivery copy
-> linkedin-scheduler.yml
-> linkedin-publish-relay.yml
-> GitHub OIDC
-> Bridge exact prepublication checks
-> LinkedIn immediate publication when due
```

A connection, `planned_at`, `approved` state or stored token is never by itself a runtime mutation grant.

## Credential health and renewal

Bridge `0.10.0+` exposes read-only LinkedIn credential verification through the common `social_connection_health` operation.

The check confirms that the stored credential still authenticates and that returned member identity matches the stored verified member. It returns no access token.

The skill combines this live result with the token expiration timestamp stored in user/project data.

Default warning states:

```text
> J-30 -> healthy
J-30..J-15 -> renewal_due_30
J-14..J-8 -> renewal_due_14
J-7..expiry -> renewal_required_7
expired or provider-invalid -> expired_or_invalid
```

If any scheduled LinkedIn post occurs at or beyond the effective known expiry, surface renewal before that post even if the general warning window has not yet been reached.

## Renewal path

When renewal is required:

```text
reuse existing application/product/callback configuration
-> reconnect through SEO Workflow Bridge
-> complete LinkedIn OAuth again
-> verify the same intended member identity
-> persist the new non-secret expiry/health metadata in the active user profile
```

Do not recreate the application merely because an access token expired.

If the verified remote member changes unexpectedly, fail closed and require explicit resolution before future publication.

## Resume-first behavior

On every activation/reconnect request:

1. load the active user profile;
2. inspect current Bridge LinkedIn state read-only;
3. compare verified member identity and expiry metadata;
4. resume at the first incomplete/invalid milestone;
5. do not repeat completed developer-application setup unnecessarily;
6. never request a raw access token in chat;
7. persist verified non-secret changes immediately.

## Completion

LinkedIn onboarding is complete when:

- required products/scopes are active;
- exact callback is configured;
- Bridge connection is enabled;
- the intended member identity is verified;
- token remains only WordPress-side;
- non-secret identity/expiry metadata is recoverable from user/project data;
- scheduler/relay readiness is independently configured when unattended publication is desired.
